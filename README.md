# AI-Assisted Selenium Test Maintenance

> **Note:** All instructions in this README are written for **Windows**. Commands, paths, and the Jenkins pipeline are Windows-specific.

An AI-assisted Selenium test-maintenance project that demonstrates how existing Java + Selenium + Page Object Model (POM) automation can be updated when an application's UI changes.

The project goes beyond simple locator self-healing. The AI is provided with the old and updated UI (HTML + screenshots) along with the existing automation code. It analyzes the changes and generates the Java Page Object and test-class changes required for the updated application.

## How Do You Want to Explore This Project?

### Option A — Just want to see the result (no setup required)

If you just want to see what the AI-assisted maintenance produced, without running anything yourself:

1. Clone the `master` branch — this is the original V1 automation.
2. Clone the `v2-ai-migration` branch — this is the AI-updated V2 automation.
3. Compare the Page Object and test classes under `src/test/java` between the two branches to see exactly what the AI changed.
4. Open the HTML execution report already committed in each branch under `reports/` to see the result of that branch's test run.

See [Branches](#branches) below for what each branch contains, and [What a Good AI Update Looks Like](#what-a-good-ai-update-looks-like) for a summary of the expected changes.

### Option B — Hands-on, run the whole process yourself

If you want to go through the full workflow — run V1, hand the project to an AI, apply the AI-generated changes, and run V2 — follow the [Execution](#execution) and [AI Migration Demonstration](#ai-migration-demonstration) sections below.

## Project Objective

In a normal Selenium project, an application UI change can require changes to:

* Element locators
* Page Object elements and methods
* Test actions
* Navigation
* Workflow steps
* Newly introduced fields

This project demonstrates using AI to analyze those changes **before test execution** and update the existing Selenium automation accordingly — identifying not just locator changes, but changed labels, added/removed elements, changed interactions, and changed navigation/workflow, while preserving the existing framework structure, Page Object design, and coding style.

The basic flow is:

```text
Old Application UI
  ├── HTML
  └── Screenshot
          +
New Application UI
  ├── HTML
  └── Screenshot
          +
Existing Selenium Automation
  ├── Page Objects
  └── Test Classes
          |
          v
    AI Change Analysis
          |
          v
 Updated Page Objects / Tests
          |
          v
 Execute Automation Against New UI
```

It is not intended to be a general-purpose Selenium self-healing platform.

### `demo-app`

Contains the sample application used to demonstrate the maintenance process.

* `v1` = original application
* `v2` = updated application

The application is intentionally small so that the effect of UI changes on Selenium automation can be clearly demonstrated.

### `maintenance`

Contains the evidence used by the AI to understand the application changes.

```text
maintenance/
├── current/
│   ├── html/
│   └── screenshots/
│
└── updated/
    ├── html/
    └── screenshots/
```

The file names correspond to the relevant Page Object.

For example:

```text
CustomerDetailsPage.java
maintenance/current/html/CustomerDetailsPage.html
maintenance/current/screenshots/CustomerDetailsPage.png
maintenance/updated/html/CustomerDetailsPage.html
maintenance/updated/screenshots/CustomerDetailsPage.png
```

Both HTML and screenshots are used because HTML provides DOM/element information while screenshots provide visual and contextual information.

### `src/test/java`

Contains the Selenium automation.

The main components are:

* Page Objects
* Test classes
* Reusable Selenium actions
* Driver setup
* Reporting utilities
* Global test configuration

### `reports`

Contains execution reports and screenshots generated by the automation.

## What a Good AI Update Looks Like

For a change of the scope demonstrated in this project (relabeled fields, renamed locators, a renamed button, one added navigation step), the AI should be able to produce close to a complete, working update on its own — roughly **90%+ of the required changes handled directly by the AI**, with little to no manual code editing needed afterward to get V2 passing.

What manual involvement should typically remain limited to:

* Reviewing the AI's diff before applying it.
* Supplying real values for any genuinely new field where no existing test-data source applies (the prompt asks the AI to leave these as an appropriately named empty variable rather than inventing a data source).

If a change requires far more manual correction than that, it's a sign the change was outside what a single-pass AI review can reliably handle (e.g. a deeper workflow or backend change), rather than a locator/UI-level update.

## Execution

There are **two ways to execute the project**.

### Option 1 — Manual Execution

This is useful when running and demonstrating the project locally.

#### 1. Start the application

Open a terminal in the project directory.

Run the following commands to host the application:

```bash
cd demo-app
python -m http.server 8000
```

The application will be available at:

```text
http://localhost:8000/v1/login.html
```

or:

```text
http://localhost:8000/v2/login.html
```

#### 2. Configure the automation URL

Open:

```text
src/test/java/resources/GlobalSettings.properties
```

Set:

```properties
application_url=http://localhost:8000/v1/login.html
```

or for V2:

```properties
application_url=http://localhost:8000/v2/login.html
```

The URL must point to the application version currently being tested.

#### 3. Run the Maven test

From the project root:

```bash
mvn test
```

The Selenium test will start the browser and execute the automation against the configured application.

#### 4. Stop the application

After testing, stop the Python HTTP server with:

```text
Ctrl + C
```

Close the terminal.

To run the other application version, open a fresh terminal and repeat steps 1–4 with the matching `application_url` value.

---

### Option 2 — Jenkins

The project also contains a `Jenkinsfile` that automates the setup and execution.

The Jenkins job provides three parameters:

|Parameter|Purpose|
|-|-|
|`PROJECT_PATH`|Local path of the project|
|`APP_PORT`|Port on which the application is started|
|`APP_VERSION`|Application version to test (`v1` or `v2`)|

Example:

```text
PROJECT_PATH = D:\SUJAN\GitHubRepo\ai-selenium-test-maintenance
APP_PORT     = 8000
APP_VERSION  = v1
```

The Jenkins pipeline:

1. Checks for the required tools.
2. Downloads Java 21 if required.
3. Downloads Maven 3.9.12 if required.
4. Downloads Python 3.14.7 if required.
5. Dynamically creates the application URL using the selected port and application version.
6. Updates only `application_url` in `GlobalSettings.properties`.
7. Starts the selected application using Python's HTTP server.
8. Runs `mvn test`.
9. Stops the application server after execution.

The tools are kept inside the project's `tools` directory so that the Jenkins job does not depend on globally installed Java, Maven, or Python versions.

See [`requirements.md`](requirements.md) for what the Jenkins agent itself needs (Chrome, display/headless considerations, and internet access).

## AI Migration Demonstration

The recommended demonstration flow is:

### Step 1 — Run V1

Start the V1 application and run the existing Selenium automation.

Confirm that the original automation passes and review the generated report.

### Step 2 — Understand the V2 changes

The `maintenance` folder contains the old and updated HTML/screenshots that represent the application change.

### Step 3 — Give the project to an AI

To update your automation suite, you must feed your current test infrastructure into an advanced LLM.

* Delete the hidden `.git` folder from your local copy of the project.
* Compress the entire project folder into a standard `.zip` file.
* Open Claude AI in your web browser, start a new chat, and upload the zipped project directly to the prompt interface.
* Copy and paste your specific maintenance prompt alongside the uploaded file, and submit it.

The AI will analyze the differences between the V1 UI structure, the V2 UI structure, and your existing Selenium automation. It will generate the updated Java source code for the classes that need to change to reflect the necessary locator and structural changes.

AI output can vary between runs — review the generated classes against the notes in [What a Good AI Update Looks Like](#what-a-good-ai-update-looks-like) before applying them.

### Step 4 — Apply the AI-generated classes

Replace only the affected Java classes with the classes generated by the AI.

Do not replace the entire framework.

### Step 5 — Run V2

Before running, update `GlobalSettings.properties` to point `application_url` at the V2 application — the AI is instructed not to touch this file, so this step is done manually.

Run the updated automation against V2 using either:

* Manual execution, or
* Jenkins with `APP_VERSION = v2`

### Step 6 — Verify the result

The objective is to demonstrate that the AI-generated automation successfully handles the application changes.

## AI Maintenance Prompt

Use the following as your specific maintenance prompt:

```text
The application has been upgraded, and the existing Selenium automation needs to be updated to work with the new UI.

Review the existing Selenium automation under `src/test/java`, including the Page Objects and test classes, to understand the current framework structure, automation flow, page interactions, and navigation.

Then analyze the old and new application using the files under:

- `maintenance/current/`
- `maintenance/updated/`

Use both the screenshots and HTML to identify changes between the old and updated UI.

### Scope

Only use:

- `src/test/java` to understand and update the Selenium automation.
- `maintenance/current/` and `maintenance/updated/` to understand UI changes.

Do NOT inspect, analyze, modify, or use anything under `demo-app/`.

Do NOT modify:

- Application files
- `GlobalSettings.properties`
- URLs or application versions
- `pom.xml`
- Jenkins/CI configuration
- Unrelated framework files

The application itself is outside the scope of this task. Your job is to update the automation to work with the updated application.

### Analyze the complete automation flow

Do not limit the analysis to locator changes.

Identify changes such as:

- Locator changes
- Added or removed elements
- Changed fields or labels
- Changed element structure
- Changed page interactions
- Changed navigation
- Added or removed workflow steps

Consider the complete test flow and determine how the updated UI affects the existing Page Objects and test classes.

Pay particular attention to the application state and navigation after each significant action. Ensure the updated automation follows the correct user journey in the new application.

### Code changes

Update only the Page Object and test classes that are actually affected.

Preserve the existing:

- Framework structure
- Page Object design
- Coding style
- Naming conventions
- Reusable methods
- Test-data approach

Make the minimum changes required for the updated application.

Do not refactor or rewrite unrelated working code.

For newly introduced fields or test data where no existing data source can be inferred, use an appropriately named empty variable rather than introducing a new data-source mechanism.

### Output

Return ONLY the Java classes that require modification.

Do NOT return:

- The complete framework
- A ZIP of the project
- `demo-app`
- Configuration files
- Unchanged Java classes
- Other unrelated files

For each class that requires modification, provide the complete updated Java source code so it can directly replace the existing class.

If a class does not require changes, do not include it.

Before providing the output, verify that the modified automation correctly reflects the UI changes and complete workflow represented by the updated application.
```

## Branches

The repository contains two branches representing the two stages of the AI-assisted maintenance process.

* **`master`** — V1 automation: the Selenium automation as it exists before any AI-assisted maintenance, running against the V1 application. The latest V1 HTML execution report is also present in this branch.
* **`v2-ai-migration`** — AI-updated V2 automation: the same automation after applying the AI-generated changes, running against the V2 application. The latest V2 HTML execution report is also present in this branch.

## Current Limitations

This project is an MVP/portfolio prototype and does not attempt to solve every automation-maintenance problem. It currently does not aim to provide:

* Backend/API change handling
* Business-requirement understanding
* Fully autonomous test-data sourcing
* Automatic Git branching or pull requests
* Automatic code review
* Production-scale deployment
* Complete handling of every possible Selenium failure
* A custom LLM

The project should also not be judged only by whether AI can find a replacement XPath. The more relevant question is whether the AI can understand how the application changed — Page Objects, locators, elements, actions, navigation, and test flow — and correctly update the existing Java/Selenium/POM automation to match, while preserving the existing framework wherever possible.
